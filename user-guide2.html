1Get set up

You don't need to be technical, and you never touch a terminal. It's a one-time, ~10-minute setup: install one free app, then ask Claude — in plain English — to fetch the workspace for you. Claude runs the technical bits and asks your permission first; you just click Allow.

Where this lives — the workspace is a project hosted on GitHub. This is the page it comes from:

tekiondesignteam / design-specgithub.com/tekiondesignteam/design-spec ↗

You don't download anything from that page by hand — Claude fetches it for you in Step 3. It's just where the workspace lives, in case you want to look.

Step 1 — Install the Claude desktop app

This is the app you'll do everything in — Claude Code is built right in, so there's nothing else to install. Download it from claude.ai/download, open it, and sign in with your work account.

One small requirement Claude needs to fetch the workspace: Git. Most Macs already have it. If yours doesn't, the app will offer to install it the first time it's needed — just say yes.

Step 2 — Open Claude Code and pick a folder

  • In the app, click the Code tab at the top, then + New session.
  • Use the Project folder picker (in the message area) to choose where the workspace should live — your Desktop is a fine choice. You can also drag a folder in.

Step 3 — Ask Claude to fetch the workspace

Type this message to Claude and send it, word for word:

You Clone https://github.com/tekiondesignteam/design-spec into this folder, then install the pre-commit hook from its hooks/ folder.

Claude will ask permission before it runs anything — click Allow. When it's done, you'll have a new design-spec folder, and a safety guardrail is switched on that quietly keeps the shared design systems read-only (so you can only ever change your own work — nothing breaks for anyone else). You don't need to understand it; it just protects you.

Step 4 — Point Claude at the workspace

Start a + New session and set the Project folder to the design-spec folder Claude just created. That's the workspace — everything you build lives inside it.

Step 5 — Start building

That's the whole setup. From here you just tell Claude what you want in plain English. Two shortcuts speed up the two main steps — type them, or just say the same thing in words:

  • /new-project — or "start a new project called vehicle-search using the t1 design system" (§5, step 1)
  • /spec — or "turn this PRD into a spec" (§5, step 2)
Next time you want to work, there's nothing to reinstall: open the app → Code → + New session → set the folder to design-spec. Steps 1–3 are one-time only. Ready to build? Head to §5 — The workflow.

2The idea in one minute

Long AI sessions drift: Claude fills gaps with guesses and forgets decisions made an hour ago. This workspace fights that with a chain of small artifacts you approve one at a time.

Each project lives in its own folder under projects/<name>/ and is pinned to one design system (t1, alloy, …). The design system is the source of truth for look, type, spacing, and components — you never invent visual style, you inherit it.

The deliverable is always a single HTML file you can open in a browser. No build tools, no bundlers.

3Before you start

  • Prototypes are opened through a local web link (Claude sets this up for you), not by double-clicking the file. (Double-clicking uses file://, which browsers block for these prototypes.) See §7.
  • You work only inside your own projects/<name>/ folder. Everything under design-systems/ is read-only — a commit that touches it is blocked automatically (that's the guardrail from §1).
  • Pick your design system up front. Designers can't add new ones; ask a maintainer if the system you need isn't listed.

Not sure which design systems are available? Just ask Claude:

You Which design systems can I use in this workspace?

4The five artifacts

Everything Claude builds traces back to these files. You read and approve them; Claude fills them in.

FileWhat it isWho writes it
constitution.mdThe fixed frame: boundaries + the design system's visual language. Read this first.Generated by /new-project, then you review
spec.mdWhat you're building: the problem, scope, user flows, components, states, and acceptance criteria (AC-1, AC-2, …)./spec, with your input
plan.mdThe build broken into small, checkpointed steps.You + Claude
tasks.mdA checklist — one line per behavior, each citing an acceptance criterion. Also the drift log.Claude, as it builds
reviews/step-N.mdScreenshots + checks proving each step matches the spec, at every breakpoint.Claude, at each checkpoint
Acceptance criteria (AC-n) are the backbone. Every task cites the AC it satisfies, and every review frame proves an AC is true in the browser. If it isn't in the spec as an AC, it doesn't get built.

5The workflow, step by step

  1. Scaffold the project

    /new-project <name> [design-system]
    • <name> is lowercase, kebab-case, no spaces (e.g. vehicle-search).
    • If you skip the design system, Claude lists the options and asks you to pick.

    This creates projects/<name>/ with the four template files and a RUN.md, and fills the constitution from the chosen design system. Nothing gets designed yet.

    → Then: read constitution.md. Does the visual direction and the boundary look right?

  2. Write the spec

    /spec <name> <your PRD>

    The source can be pasted text, a Confluence/Jira link, a Figma link, a URL, or a file path. Claude saves it to brief.md so the spec is traceable.

    Claude then scores your brief on six dimensions (problem, scope, flows, components, states, acceptance criteria) and only asks about the gaps. Anything you skip stays a visible {{TODO}}, never an invented requirement.

    → Then: read spec.md. This is where you kill ambiguity. Be concrete — name real components, real states, real copy. Vague specs produce vague UI.

  3. Plan the build

    Ask Claude to fill in plan.md: order the work so each step is small and reviewable — shell/layout first, then sections, then states (empty / loading / error / success), then polish.

  4. Build, one checkpoint at a time

    Claude builds step by step. Before each step it re-reads the constitution and spec; after each step it records a reviews/step-N.md walkthrough — screenshots at every breakpoint, plus checks a screenshot can't prove (element counts, scroll behavior, "the rest of the screen didn't change").

    Then it stops and waits for you to review before moving on. Checkpoints are where drift gets caught — use them. Review reviews/step-N.md, then tell Claude to continue.

  5. Done

    A screen is done when it uses only the design system's tokens and components, every state in the spec is built, it renders at every breakpoint, and nothing outside your project folder changed. tasks.md tracks all of this.

6The rules Claude follows

So you know what to expect:

One folderOnly projects/<name>/ is ever modified.
One design systemNo mixing, borrowing, or inventing tokens. A missing piece is logged as a gap in the constitution, not faked.
One HTML file, no build stepPlain HTML/CSS/JS, or React via in-browser Babel. Never a Vite/webpack app that must be compiled.
Every state, every breakpointEmpty, loading, error, and success — verified visually and with a DOM check.
Drift is logged, not hiddenIf the UI diverges from the spec, it goes in the drift log in tasks.md and the spec is updated first.
kebab-case filenamesNo spaces, no leading _ — they break URLs and hosting.
Want to intentionally break from the design system? That's a deviation — it gets recorded in constitution §5 with a reason. Nothing silent.

7Running your prototype

The simplest way — just ask Claude, and click Allow when it asks:

You Serve this repo locally and give me the link to open my prototype.

Claude starts a little local web server and hands you a http://localhost/… link. Don't double-click the HTML file — opening it directly (as file://) is blocked for any prototype that loads its design-system bundle. If you'd rather run it yourself, your project's RUN.md has the exact command (it's python3 -m http.server from the repo root).

  • Sharing outside the repo? Ask for a Portable build — a self-contained file that inlines the kit so it opens by double-click (see plan.md).
  • Hosting for a team? GitHub Pages gives every project a real https:// link (see DEPLOY.md). Note this publicly exposes the design system — prefer a Portable build for internal-only work.

8Getting better results

  • Be specific in the spec. "A card with the vehicle photo, price in bold, and a disabled Reserve button when out of stock" beats "a nice vehicle card."
  • Name the unhappy paths. Empty results, no permission, network error — these are the #1 cause of "this isn't what I wanted."
  • Approve at every checkpoint. Don't let Claude build five steps then review. Small reviews catch drift cheaply.
  • Re-read the constitution when a session gets long — and ask Claude to as well. It's the anchor.
  • Want the design pushed further? Ask Claude to use the impeccable skill for a design-quality pass (hierarchy, spacing, states, accessibility).
