# Designer's Guide

Welcome. This repo is a **spec-driven design workspace**. You describe *what* you want to build — grounded in a real design system — and Claude builds a working, reviewable prototype without drifting from your intent.

This guide is for designers. You do not need to write code. You do need to be concrete about what you're building.

---

## 1. The idea in one minute

Long AI sessions drift: Claude fills gaps with guesses and forgets decisions made an hour ago. This workspace fights that with a chain of small artifacts you approve one at a time:

```
constitution  →  spec  →  plan  →  tasks  →  build  →  reviews
   (frame)      (what)   (order)  (checklist) (HTML)  (evidence)
```

Each project lives in its own folder under `projects/<name>/` and is pinned to **one** design system (`t1`, `alloy`, …). The design system is the source of truth for look, type, spacing, and components — you never invent visual style, you inherit it.

The deliverable is always **a single HTML file** you can open in a browser. No build tools, no bundlers.

---

## 2. Before you start

- Prototypes are served over a local web address, **not** by double-clicking the file. (Double-clicking uses `file://`, which browsers block for these prototypes.) See §6.
- You work **only** inside your own `projects/<name>/` folder. Everything under `design-systems/` is read-only — a commit that touches it is blocked automatically.
- Pick your design system up front. Designers can't add new ones; ask a maintainer if the system you need isn't listed.

Check which design systems exist:

```
ls design-systems/
```

## 3. The five artifacts

Everything Claude builds traces back to these files. You read and approve them; Claude fills them in.

| File | What it is | Who writes it |
|------|-----------|---------------|
| `constitution.md` | The fixed frame: boundaries + the design system's visual language. Read this first. | Generated by `/new-project`, then you review |
| `spec.md` | *What* you're building: the problem, scope, user flows, components, states, and acceptance criteria (`AC-1`, `AC-2`, …). | `/spec`, with your input |
| `plan.md` | The build broken into small, checkpointed steps. | You + Claude |
| `tasks.md` | A checklist — one line per behavior, each citing an acceptance criterion. Also the drift log. | Claude, as it builds |
| `reviews/step-N.md` | Screenshots + checks proving each step matches the spec, at every breakpoint. | Claude, at each checkpoint |

**Acceptance criteria (`AC-n`) are the backbone.** Every task cites the AC it satisfies, and every review frame proves an AC is true in the browser. If it isn't in the spec as an AC, it doesn't get built.

## 4. The workflow, step by step

### Step 1 — Scaffold the project

```
/new-project <name> [design-system]
```

- `<name>` is lowercase, kebab-case, no spaces (e.g. `vehicle-search`).
- If you skip the design system, Claude lists the options and asks you to pick.

This creates `projects/<name>/` with the four template files and a `RUN.md`, and fills the constitution from the chosen design system. **Nothing gets designed yet.**

→ Then: read `constitution.md`. Does the visual direction and the boundary look right?

### Step 2 — Write the spec

```
/spec <name> <your PRD>
```

The source can be pasted text, a Confluence/Jira link, a Figma link, a URL, or a file path. Claude saves it to `brief.md` so the spec is traceable.

Claude then scores your brief on six dimensions (problem, scope, flows, components, states, acceptance criteria) and **only asks about the gaps** — it won't interrogate you on what's already clear. Anything you skip stays a visible `{{TODO}}`, never an invented requirement.

→ Then: read `spec.md`. This is where you kill ambiguity. Be concrete — name real components, real states, real copy. Vague specs produce vague UI.

### Step 3 — Plan the build

Ask Claude to fill in `plan.md`: order the work so each step is small and reviewable — shell/layout first, then sections, then states (empty / loading / error / success), then polish.

### Step 4 — Build, one checkpoint at a time

Claude builds step by step. Before each step it re-reads the constitution and spec; after each step it records a `reviews/step-N.md` walkthrough — screenshots at every breakpoint the design system defines, plus checks a screenshot can't prove (element counts, scroll behavior, "the rest of the screen didn't change").

**Then it stops and waits for you to review** before moving on. Checkpoints are where drift gets caught — use them. Review `reviews/step-N.md`, then tell Claude to continue.

### Step 5 — Done

A screen is done when it uses only the design system's tokens and components, every state in the spec is built, it renders at every breakpoint, and nothing outside your project folder changed. `tasks.md` tracks all of this.

## 5. The rules Claude follows (so you know what to expect)

- **One folder.** Only `projects/<name>/` is ever modified.
- **One design system.** No mixing, no borrowing, no inventing tokens. A missing piece is logged as a *gap* in the constitution, not faked.
- **One HTML file, no build step.** Plain HTML/CSS/JS, or React via in-browser Babel. Never a Vite/webpack app that must be compiled.
- **Every state, every breakpoint.** Empty, loading, error, and success — verified visually and with a DOM check.
- **Drift is logged, not hidden.** If the built UI diverges from the spec, it goes in the drift log in `tasks.md` and the spec gets updated first.
- **kebab-case filenames, no spaces, no leading `_`** (they break URLs and hosting).

If you want to intentionally break from the design system, that's a **deviation** — it gets recorded in constitution §5 with a reason. Nothing silent.

## 6. Running your prototype

Serve the repo over a local web address, then open your file:

```
cd <repo-root>
python3 -m http.server 4599
# open http://localhost:4599/projects/<name>/<file>.html
```

Your project's `RUN.md` has the exact command. **Don't double-click the HTML file** — `file://` is blocked for any prototype that loads its kit bundle.

- **Sharing outside the repo?** Ask for a **Portable build** — a self-contained file that inlines the kit so it opens by double-click (see `plan.md`).
- **Hosting for a team?** GitHub Pages gives every project a real `https://` link (see [DEPLOY.md](DEPLOY.md)). Note this publicly exposes the design system — prefer a Portable build for internal-only work.

## 7. Getting better results

- **Be specific in the spec.** "A card with the vehicle photo, price in bold, and a disabled Reserve button when out of stock" beats "a nice vehicle card."
- **Name the unhappy paths.** Empty results, no permission, network error — these are the #1 cause of "this isn't what I wanted."
- **Approve at every checkpoint.** Don't let Claude build five steps then review. Small reviews catch drift cheaply.
- **Re-read the constitution when a session gets long** — and ask Claude to as well. It's the anchor.
- **Want the design pushed further?** Ask Claude to use the `impeccable` skill for a design-quality pass (hierarchy, spacing, states, accessibility).
